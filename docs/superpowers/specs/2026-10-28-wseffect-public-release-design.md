# wseffect public release — design specification

**Status:** Approved by the user on 2026-10-28. **Goal:** move wseffect to a canonical public GitHub repository, publish five coordinated npm packages, and launch a complete Astro documentation site at `https://wseffect.com` so a new developer can follow Getting Started and build a working application.

## Goal, users, and success

**Users:** TypeScript developers evaluating or building with wseffect; maintainers publishing the packages; contributors reporting issues or making changes; agents consuming the Markdown documentation.

**Success criteria:**

1. `wsagency/wseffect` is the sole canonical, public source repository with preserved, audited history; the old Gitea repository is archived only after verification.
2. All five `@wsagency/wseffect-*` packages are publicly installable at coordinated `0.1.0-rc.0`, with `next` as the prerelease channel and `latest` explicitly aligned with each RC until `0.1.0`.
3. `wsagency/wseffect-web` builds and deploys an accessible, searchable, static-first Astro site from published npm packages only.
4. **Definition of done:** on a clean machine, a developer follows the `wseffect.com` Getting Started guide, runs `pnpm add @wsagency/wseffect-*@next` (the exact concrete package list/peer dependencies shown on that page), and obtains a working app by following either starter. Both downloadable starters install and build against the published registry release without local workspace links or tarballs.
5. Every public package export is represented in site inventory/navigation or an explicit grouped reference; all package notices and source/license attribution remain available.
6. The local release/deploy workflow refuses dirty, stale, unverified inputs and has tested rollback and smoke contracts.

All five packages participate in one coordinated version: `@wsagency/wseffect-app`, `@wsagency/wseffect-themes`, `@wsagency/wseffect-foldkit`, `@wsagency/wseffect-foldkit-ui`, and `@wsagency/wseffect-vite-plugin`. Ensure useful description, keywords, author/maintainer attribution, and `engines` reflect actual verified runtime requirements. - Add consumer-facing READMEs to Foldkit, Foldkit UI and Vite plugin: exact npm install commands for RC and stable form, required peer/dependency setup, scoped import examples, principal API purpose, supported runtime, and links to the full docs. Keep app and Themes consumer material and align them with the new release instructions.
- For Foldkit, Foldkit UI and Vite plugin, make each `UPSTREAM.md` README link valid by including the file in the npm `files` allowlist, or remove/replace the link with a shipped notice that preserves attribution. Preferred design: ship `UPSTREAM.md` in each package. Keep `THIRD-PARTY-NOTICES.md` and full upstream license texts.
- Ship a per-package WS Agency trademark/brand notice in every tarball. State that MIT covers code only, grants no rights to WS Agency name/logo, and that the project is unofficial/not endorsed by relevant upstream rights holders where applicable. Keep upstream licenses/copyright notices unchanged.
- Exclude generated test-only artifacts and declaration maps from tarballs when not an intentional public export. Foldkit's explicitly exported test and test/vitest APIs remain public; do not exclude files needed by these exports. Remove Foldkit UI test-named dist outputs and unneeded declaration maps where safe. Re-inspect actual tarballs rather than relying on `files` intent.
- Update each package changelog with coordinated RC heading and package-specific release notes; do not introduce stable claims in an RC.
- Update `scripts/check-repo.ts` and its tests: replace the hard-coded `0.0.0` requirement with a release-aware guard that accepts the prepared coordinated RC version and verifies all package versions align, release metadata is public/canonical, `private:false`, and the chosen tag is `next`. Keep ordinary development workflow usable before release without weakening package correctness checks.

### Dependency order

Compute a topological order from the five manifests, fail on cycles or undeclared internal edges, and use that computed result in `docs/RELEASING.md` and scripts. Current graph evidence gives this publish order: **Foldkit → Foldkit UI → Themes → Vite plugin → app**. Foldkit is the common base; UI and Themes consume core; plugin consumes core; app consumes the package set. Before the first run, script output must print the graph edges and order so an operator verifies it against manifests; do not maintain a separate unvalidated hard-coded package sequence.

### Local release runbook and scripts

Add `docs/RELEASING.md` with a checklist and exact commands for: clean origin/main preparation; Effect 4.0.7 pins and `^4.0.5` published peer ranges; coordinated version/tag check; full `pnpm check`; release tag; fresh detached worktree at tag; frozen install/build; graph-derived package order; pack; manifest/tarball inspection; dry-run; isolated npm config and web 2FA; sequential publish; explicit `latest` dist-tag updates; registry verification; cleanup; and rollback/stop conditions. Publishing operator is klukacin; never store credentials in repo, shell profile, or the release package directory.

Add local scripts for deterministic preflight, packing/inspection, and publish verification (no CI workflow). Model tarball inspection on the house workflow: inspect `package/package.json`, tar listing, export targets, expected docs/licensing/UPSTREAM files, internal ranges rewritten to exact same RC, repository URL, no `workspace:`, `file:`, or `link:` dependencies, no test artifacts except intentionally exported API, and scan contents for secrets and host paths. Hash tarballs and preserve checksums in a release record. Run `npm publish --dry-run` on every archive before actual publish. Copy finalized tarballs to the isolated temp area, outside any Git working tree; use a temporary npm userconfig, `npm login --auth-type=web`, obtain live 2FA approval, publish each archive with `--access public --tag next`, and immediately set each package's `latest` to that same RC. For the packed-consumer fixture, write a fixture-local `pnpm-workspace.yaml` whose `minimumReleaseAgeExclude` contains exactly the five local `@wsagency/*` tarballs; do not weaken the root age policy for these file-based fixture packages. Add temporary exact 4.0.7 age exclusions to the root only if implementation begins before `2026-10-29T03:00Z`, removing them once that time has passed. Verify registry metadata/integrity and both `next` and `latest` dist-tags; do not trust publish CLI output alone. ## Website design: `wsagency/wseffect-web`

Astro owns prose and publishing concerns that benefit from a static content framework; wseffect is used where it adds product-specific value: rendering real component examples at build time and powering interactive demos. This answers the question of Astro compatibility: the spike successfully used wseffect with Astro without a dedicated adapter or the wseffect Vite plugin, invoked `renderToString` from Astro frontmatter during static generation, and ran `Runtime.embed` islands in Chromium, Firefox and WebKit (`site-spike/REPORT.md`, §§Verdict, Verification). The documented production design keeps docs pages JavaScript-free and bounds the experimental server API behind a tested helper.


### Repository and published-package contract

Separate public repository; no workspace member, local `link:`, monorepo import aliases, tarball fallback, or reading package source at build time. Pin exact published versions in lockfile and package metadata; launch site uses the `0.1.0-rc.0` packages. Build-test an update by changing exact version pins after registry verification. Pin Node, pnpm, Astro, Foldkit, Wrangler and browser dependencies. Since site receives only published packages, generated inventories/Props derive from their exported runtime declarations/schema at build time or checked release-generated manifests included in published packages; never depend on unshipped source. Package public export inventory is compared with site inventory so omissions fail.

### Website `pnpm check`

One local check command must run in deterministic order and fail on each stage: (1) Astro production build; (2) inventory, route, canonical URL, local link, HTML and Markdown twin consistency checks; (3) generated Props/export checks and snippet compile; (4) each of two downloaded starter projects independently installs from the registry and builds (including codegen for full app); (5) browser tests in Chromium, Firefox, WebKit for search, representative component interaction, portal stacking/focus, keyboard behavior, responsive layout, 404 and Markdown negotiation; (6) axe accessibility checks on main docs and representative interactive pages. This is local-only, not GitHub Actions. It does not turn performance into a gate; retain a manually recorded report.

### Worker HTTP contract

Worker uses static assets with `run_worker_first` and extension-aware route fallback. It must serve missing assets as 404, never the app/page HTML; extensionless paths may serve their generated route or fall back to `/index.html` only for valid page route requests. Header rules apply consistently to success and not-found responses.

| Path/request | Status | `Cache-Control` |
|---|---:|---|
| `/_astro/<content-hash>.*` and other fingerprinted static assets | 200 | `public, max-age=31536000, immutable` |
| Existing `/...` HTML page / `/index.html` | 200 | `no-cache` |
| `/robots.txt`, `/sitemap-index.xml`, sitemap children, generated Markdown twins | 200 | `no-cache` (revalidate generated content) |
| `/version.json` | 200 | `no-cache` |
| Extensionless known page (`/`, `/getting-started/`, etc.) | 200 | `no-cache` |
| Extensionless unknown route | 404 page | `no-cache` |
| Missing file with an extension, including missing JS/CSS/image/font | 404 | `no-cache` |
| Markdown negotiation on known extensionless page, GET/HEAD and accepted Markdown type | 200 (Markdown twin) | `no-cache`; include `Vary: Accept` |
| Markdown negotiation on unknown path, unsupported method, or non-Markdown Accept | Normal Worker/static behavior; 404 for unknown route | `no-cache` on error/page response |
| `https://www.wseffect.com/<path>?<query>` | 301 to `https://wseffect.com/<path>?<query>` | Zone redirect; preserve path and query |

Worker tests assert all table rows including HEAD parity, query preservation, extension-aware 404, `Vary`, and redirects preceding negotiation. Astro's default hashed asset directory is `/_astro/`; before deploy, merge current plus previous three releases' `/_astro/` hashed asset trees from a local release store into `out/`, retaining the release SHA mapping. Check Cloudflare Workers static asset file-count/size limits before adoption and every release. Do not assume native Worker asset versions retain old assets.

### Local Worker deployment safeguards

`wseffect-web` includes a pinned local deploy script; no CI deploy. Use an exclusive lock (`flock`/equivalent); require current branch `main`, fully clean working tree including untracked files, fetch origin and assert `HEAD == origin/main`. Record SHA. Create a fresh worktree at that SHA outside the user's checkout, install with frozen lockfile, delete prior `out/`, and run `pnpm check` in this same run. Verify build artifact created now; `version.json` contains SHA; headers, fallback and Worker entry present; no secrets/host paths; npm dependencies resolve to exact published package versions and contain no workspace links. Merge the previous three releases' assets; verify count/size limits and collisions. Fetch/re-check `origin/main == SHA` after build. Only then run `pnpm exec wrangler deploy --message <SHA>` from the same build tree, passing the scoped token only in the wrangler process environment. Token comes from workstation libsecret/pass; never export it to general shell, write it to disk in repo, or expose it to build/test processes. Smoke-check deployed SHA, headers, missing assets, extensionless route, Markdown negotiation, and `www` 301. Record SHA, Worker version ID and smoke result in release record. Roll back with `wrangler rollback` to preceding Worker version; if unavailable, redeploy the preceding verified SHA/artifact.

## Risks and mitigations

- **Public history exposes secrets/internal content:** pre-push history audit and remediation; compare all refs; stop before public push on unresolved finding.
- **Effect lifecycle tests / compatibility:** 4.0.9 is nonexistent; 4.0.7 is latest stable. Use only the diagnosed test fixture/synchronization fixes, without changing Foldkit runtime; keep all five published `effect` and `@effect/platform-browser` peer ranges at `^4.0.5`. Diagnosis reports full check/e2e passed at 4.0.7, with the Effect shell Brotli delta at +1,270 B (+1.70%), below GATE-S3 threshold.
- **Coordinated package skew or wrong graph order:** derive graph from manifests, gate all versions/internal peers, publish sequentially and stop on first failure; registry-check all five before website pinning.
- **Manual 2FA/registry propagation delays:** reserve klukacin for live approvals; poll registry metadata until visible; do not confuse CLI success with registry visibility; stop on partial release and use higher RC recovery.
- **No provenance:** disclose in release docs and package site; revisit only as explicit future hosted-publish decision.
- **Experimental SSR helper changes:** pin versions, narrow wrapper, unit-test render output, keep demos functional only where server-render contract passes; docs remain readable without JavaScript.
- **Portal stacking / global Themes CSS:** shared Theme and portal root; cross-engine browser tests; add CSS override only with reproducible failure and targeted regression test.
- **Stale lazy chunk after deploy:** retain hashed assets from prior three releases; check Cloudflare asset limits; smoke old chunk URL before promotion.
- **Unsafe/stale deploy artifact or token exposure:** lock, clean main == origin/main, fresh worktree, same-run check, artifact/SHA verification, final origin check, process-only secret injection, smoke and rollback.
- **Docs inventory drift / inaccurate examples:** generated package export manifest, one authoritative route inventory, compile all curated snippets, test both downloadable starters against registry packages.
- **Accessibility/search/SEO defects:** static HTML and no-JS docs, Pagefind/sitemap/robots/404 tests, axe and three-engine Playwright checks.
- **Performance regression:** manual report only; no runner exists and performance is explicitly not a launch gate.
